# Meera

A personal React + Vite messaging app using Supabase Auth, Postgres, Realtime,
Storage, and Edge Functions. Includes chats, timed snaps, stories, voice notes,
voice/video calls, private memories, rotating aliases, daily questions, and
opt-in location sharing.

## Current status

The audit fixes are implemented locally on `codex/audit-fixes`. They require the
matching database upgrade and cleanup worker. **Do not deploy this frontend
against the old schema.** See [AUDIT-FIXES.md](AUDIT-FIXES.md) for the findings
matrix, verification results, and remaining production checks.

## Local setup

```sh
npm ci
cp .env.example .env
# Fill in the public Supabase URL/anon key and optional VAPID public key.
npm run dev
```

Never put a service-role key, database password, VAPID private key, or cleanup
secret in a `VITE_` variable. Frontend environment variables ship to browsers.
Camera/microphone access requires HTTPS except on localhost.

```sh
npm run lint
npm test
npm run test:db
npm run build
```

`test:db` runs real PostgreSQL logic in an isolated PGlite database with minimal
Supabase schema fixtures. It creates no external accounts and accesses no live
user data. Browser unit tests mock network and media hardware.

## Database setup

Use the ordered files in `supabase/migrations`, not ad-hoc historical SQL files.

**Fresh project:** apply `202609060000_baseline.sql`, then
`202609060001_audit_fixes.sql`. The baseline refuses to run when Meera's
`profiles` table already exists. It is generated by `npm run db:baseline` from a
fixed order of historical schema sources; it does not delete accounts or force
friendships between real users. The new upgrade is tested for repeat application.

**Existing Meera project:** apply only `202609060001_audit_fixes.sql`. Do not
replay the baseline. If adopting Supabase CLI migration tracking, mark the
baseline as already applied to the existing project before pushing the upgrade.
Verify the target project and obtain a database backup before the production
upgrade. Historical SQL remains for provenance, not routine replay.

Disable email confirmation for the synthetic `username@meera.local` account
mapping. New clients supply recovery setup during signup; the database trigger
hashes it in the account-creation transaction and removes the plaintext fields
from stored auth metadata. Recovery setup is not retained in browser storage.

## Production rollout

1. Authenticate to the Supabase organization that owns this Meera project and
   verify its reference against `VITE_SUPABASE_URL`.
2. Apply the audit upgrade to staging, then run the two-user checks listed in
   [AUDIT-FIXES.md](AUDIT-FIXES.md). Apply the same upgrade to production during
   a coordinated rollout.
3. Deploy `push` with its VAPID secrets. Deploy `cleanup` with a long random
   `CLEANUP_SECRET`; the cleanup function authenticates requests itself.
   `supabase functions deploy cleanup --no-verify-jwt` is required when using
   its custom bearer secret. Never expose this secret to the frontend.
4. Schedule an HTTPS POST to `/functions/v1/cleanup` every 15 minutes, with
   `Authorization: Bearer <CLEANUP_SECRET>`. The worker purges expired rows,
   claims due file cleanup, and removes files through the Storage API. Failed
   deletions remain retryable; they are not falsely reported as completed.
5. Deploy the frontend with the project's public environment variables.
6. Disable **Allow public access** in Supabase Realtime settings, and have old
   app sessions reload. New call, typing, and online topics are private. Database
   policies bind each topic to one writer and its authorized reader.
7. Confirm fresh signup/recovery, two-user messaging/calling, notification
   logout, and scheduled cleanup against the live project.

Do not deploy the frontend alone: old databases lack `message_page`,
`mark_messages_seen`, `leave_seen_messages`, `answer_daily_prompt`, and
`queue_media_cleanup`.

## Behavior and privacy

- Messages use stable client IDs for retry safety. Offline text is persisted
  before the composer clears it and sends from any signed-in screen. Permanent
  failures retain the draft for explicit retry/edit; full storage is reported.
- Viewing records concrete rendered messages, and voice notes count when
  playback starts. Unsaved messages clear after three recorded visits, with
  24-hour-after-open / 31-day-unopened outer retention bounds. Saved messages
  are exempt. Call history is exempt from automatic expiry.
- Received snaps support up to six opens in the UI; images start their timer
  after loading. Stories last 48 hours and record views after their image loads.
- Daily questions use IST dates. Answers refresh while the app is active, and
  the database rejects a stale question/day combination.
- The PIN and aliases provide discretion, not encryption. The web cannot
  reliably detect screenshots or prevent recipients from copying media.
- Signed media URLs are bearer links with a limited lifetime. In-memory URLs
  are cleared on account changes; already downloaded copies are not recalled.
- Historical private message backup storage retains message rows separately
  for three days when its scheduled purge is configured. Verify that schedule
  in production; UI disappearance is not a guarantee of immediate erasure.

## Architecture

`src/lib/db.js` owns database calls; `outbox.js` owns pending text;
`privateRealtime.js` owns authenticated signaling; provider components are
separate from their hook/context modules to preserve Fast Refresh.

Core paths:

- `src/hooks/AuthProvider.jsx`, `CallProvider.jsx`, `OnlinePresenceProvider.jsx`
- `src/screens/Chat.jsx`, `Stories.jsx`, `CameraScreen.jsx`, `SnapMap.jsx`
- `src/components/OutboxDelivery.jsx`, `VoicePlayer.jsx`, `DailyQuestion.jsx`
- `supabase/migrations/`, `supabase/functions/cleanup/`, `tests/`
